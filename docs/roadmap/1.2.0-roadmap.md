# Development Roadmap — Version 1.2.0

The 1.2.0 milestone focuses on improving application architecture, extending multilingual support, and preparing Sound Lab with Healing for future user account functionality.

All features listed below are planned and must not be considered implemented until development and testing are completed. Status of items already delivered in 1.1.0 is noted per section.

- Target version: 1.2.0
- Roadmap status: Planned
- Milestones and release criteria: [1.2.0 milestones](1.2.0-milestones-and-release-criteria.md)
- Test plan: [1.2.0 test plan](../qa/1.2.0-test-plan.md)

## 1. Project Architecture Refactoring

Objective: improve maintainability, readability and scalability by separating the application into dedicated files and modules.

Status note: HTML, CSS, JavaScript and locale files were already separated in 1.1.0 (see [developer guide](../development/developer-guide.md)). The items below describe the remaining planned work.

Planned changes:
- Move styling into dedicated CSS files.
- Divide JavaScript functionality into logical modules.
- Separate audio generation and recording functionality.
- Introduce dedicated accordion and UI interaction modules.
- Introduce dedicated form validation and authentication modules.
- Centralise localisation functionality.
- Preserve all existing application features during refactoring.

Proposed project structure (may be adjusted during implementation):

```text
Sound-Lab-with-healing/
├── index.html
├── login.html
├── signup.html
├── css/
│   ├── style.css
│   ├── auth.css
│   └── responsive.css
├── js/
│   ├── app.js
│   ├── audio.js
│   ├── recording.js
│   ├── accordion.js
│   ├── validation.js
│   ├── auth.js
│   └── localization.js
├── locales/
│   ├── en.json
│   └── pl.json
├── assets/
│   └── favicon.svg
├── docs/
├── README.md
├── LICENSE
└── .gitignore
```

## 2. Multilingual Support

Objective: preserve the English interface and keep Polish localisation consistent across all screens.

Status note: English/Polish switching shipped in 1.1.0. Remaining planned work covers new screens and messages.

Planned changes:
- English remains the default language.
- Translate buttons, labels, descriptions and status messages on all new screens.
- Translate recording and audio-related feedback.
- Translate form validation messages.
- Ensure consistent language switching across application screens.

| Language | Status |
| --- | --- |
| English | Existing |
| Polish | Delivered in 1.1.0 |

Future languages may be added as the application develops.

## 3. Mock Login Screen

Objective: introduce a dedicated login interface prepared for future backend integration.

Planned fields and functionality:
- Email address.
- Password, with show/hide control.
- Remember me option.
- Forgot password link placeholder.
- Navigation to the signup screen.
- Client-side input validation with inline messages and valid/invalid indicators.
- Mock form submission.

The login interface initially simulates authentication without a real authentication service.

## 4. Mock Signup Screen

Objective: introduce a dedicated registration interface with comprehensive client-side validation.

Planned fields and functionality:
- Name.
- Email address.
- Password and confirm password.
- Terms and conditions acceptance.
- Password visibility control and password strength indicator.
- Inline validation messages and valid/invalid indicators.
- Navigation to the login screen.
- Mock form submission.

Validation requirements:

| Field | Validation |
| --- | --- |
| Name | Required, reasonable length |
| Email | Valid email format |
| Password | Minimum length and complexity |
| Confirm password | Must match password |
| Terms acceptance | Must be accepted |

Validation should give clear feedback without unnecessary interruptions.

## 5. Form Validation Architecture

Objective: create reusable validation functionality shared by login and signup forms.

Planned changes:
- Centralise validation rules and separate validation logic from presentation.
- Support validation on field blur; validate all fields on submit.
- Display contextual error messages and clear success indicators.
- Support English and Polish validation messages.
- Prevent submission when validation fails.

The validation module should be reusable when additional forms are introduced.

## 6. Future Backend Integration Preparation

Objective: design login and signup forms so a real authentication backend can be introduced without rebuilding the user interfaces.

Planned changes:
- Separate form validation from authentication logic.
- Introduce dedicated login and signup submission functions.
- Define consistent form data structures.
- Establish clear API integration points.
- Handle future server responses and errors.
- Prepare for secure authentication workflows.

Initial implementation uses mock submission functions. No real user accounts or authentication services are provided in this milestone.

Security requirement: passwords must not be stored in `localStorage` or exposed through console logs.
